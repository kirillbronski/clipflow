# Instagram: частота запросов, ожидание и HTTP 429

Исследование и требования от 27 октября 2026. Владелец сообщил, что прежняя массовая загрузка профиля останавливалась из-за частых запросов, и поручил сразу учесть ограничение частоты. Ниже требования к новой реализации, а не сообщение о готовом исправлении.

## Что подтверждено

В исходной базе 1.8.7 `source/instagram_profile.py` использует Instaloader 4.15.3 и его RateController. `request_timeout=20` ограничивает длительность запроса, а не задаёт паузу между запросами. Клиент создаётся заново для каждого обращения к профилю. HTTP 429 находится в fatal_status_codes, автоматическое продолжение после сохранённого cooldown не реализовано. Следующие отдельные посты идут через общий yt-dlp worker, без общего Instagram pacing; общий `concurrent_fragment_downloads` равен 8.

Это объясняет архитектурный пробел, но не доказывает, что именно ClipFlow исчерпал конкретный лимит. Предыдущая живая проверка получила 429 уже при web_profile_info: ранее накопленные запросы, сессия и другие приложения могли влиять на ответ. Не заявлять, что одна задержка гарантирует доступ.

Документация Instaloader объясняет, что его учёт предполагает отсутствие параллельных клиентов и ранее израсходованных запросов; частый restart/reinstantiate повышает вероятность 429. Внешняя активность Instagram неизвестна приложению. Встроенные числа RateController — эвристики библиотеки, не опубликованный контракт Instagram.

## Обязательная политика новой версии

1. Один общий Instagram request gate для получения профиля, пагинации, метаданных отдельных постов и скачивания. У каждого поста не создаётся независимый «нулевой» бюджет. Учёт авторизованной сессии и общий сервисный cooldown не сбрасываются при переходе к следующему заданию.
2. Одно активное задание Instagram; медиа карусели последовательно, параллельные фрагменты Instagram — 1. Автоматический probe качества/профиля использует тот же gate и кэш, не создаёт обходной поток запросов. Нельзя бесконечно проверять доступность во время cooldown.
3. Начальные инженерные значения: минимум 3 секунды между metadata/API HTTP-запросами; 10–20 секунд перед следующим постом и между страницами профиля. Реальная задержка — максимум требований собственного gate, стандартного RateController и сервера, а не несколько слепо сложенных sleeps. Небольшой разброс распределяет нагрузку; это не обещание обхода ограничений. Эти значения — консервативные настройки ClipFlow, не официальные «безопасные лимиты Instagram».
4. Ограничиваются новые HTTP-запросы, а не чтение каждого 64 KB блока уже начатой передачи. CDN download не нужно искусственно замедлять побайтовыми паузами. Новый CDN-запрос/фрагмент не создаётся параллельно и тоже учитывает cooldown; 429 на CDN не запускает бесконечный fallback.
5. При 429 учитывать Retry-After (секунды или HTTP-date). Без корректного заголовка — backoff 15, 30, 60 минут для последовательных отказов; встроенный limiter может требовать больше. Выбирать максимум, никогда не уменьшать серверный срок. Дополнительный jitter не делает ожидание короче. Не более двух автоматических повторов после исходного 429; третий отказ требует явного продолжения после cooldown. Retry UI не обнуляет timer. Успешно завершённый пост завершает цепочку последовательных отказов, но не отменяет ещё действующие общие сроки.
6. Cooldown и недавний учёт запросов сохраняются безопасными timestamps/counters, без cookies и signed URLs. UTC timestamps — для restart, monotonic clock — для ожидания в процессе; rollback системных часов не разрешает ранний запрос. При нескольких экземплярах общий persisted gate/lease не даёт каждой копии независимый лимит.
7. На 429 job становится paused с reason=rate_limit и next_allowed_at. Scheduler освобождает worker для YouTube/GetCourse, пропускает другие Instagram jobs до срока. В уже запущенной пользователем очереди разрешены ограниченные автоматические повторы после cooldown; после перезапуска приложения — paused до явного start/resume по общим правилам восстановления.
8. UI показывает «Instagram ограничил запросы», время разрешённого повтора, счётчик повторов, сохранённые результаты и доступные отмену/паузу. Это отдельная причина ожидания, не цикл «ошибка/скачивание» несколько раз в секунду. Cancel прерывает ожидание сразу; сетевой read ограничен timeout и не исполняется в GUI-потоке.
9. 401/403/истёкшая сессия/challenge/checkpoint не лечатся бесконечным sleep или циклом смены сессии. Показать причину и обычный пользовательский вход/подтверждение там, где он требуется. Никакой автоматической ротации IP, учётных записей или обхода challenge в этом проекте.
10. Готовые файлы и учёт завершённых постов сохраняются. При resume не скачивать их заново и не обходить уже обработанные страницы без необходимости. Cursor/checkpoint используется, пока совместим с источником; при недействительном cursor безопасно перечислить заново с дедупликацией, а не объявлять неполный список полным.
11. Диагностика содержит endpoint category, timestamp, status, выбранную задержку и retry count; не cookie/header Authorization/сырой signed URL/пароль. Версия библиотеки записывается в verification report. Возможный переход с 4.15.3 на текущую версию Instaloader — отдельная проверяемая совместимость, не слепое обновление.

## Тесты до реализации

Fake clock и инъецируемый random: minimum spacing; Instaloader/yt-dlp/probe используют один gate; Retry-After seconds/date/invalid; библиотечный срок больше собственного; jitter никогда не сокращает deadline; 429 первого/второго/третьего раза; отмена ожидания; startup не начинает сеть; restart и clock rollback не обнуляют cooldown; второй процесс не получает независимый бюджет; blocked Instagram не блокирует готовый YouTube job; CDN не делает параллельные запросы; уже готовый файл пропускается.

После unit/integration — реальные проверки доступного разрешённого профиля с наблюдаемыми интервалами и небольшим объёмом. Не делать повторные живые запросы в уже заблокированный профиль ради «проверки исправления». HTTP 429 после внедрения не скрывать и не считать положительным live-test.
