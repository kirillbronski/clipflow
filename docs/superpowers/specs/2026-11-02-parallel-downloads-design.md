# Одновременные загрузки, часть 5б

Статус: дизайн подтверждён владельцем 2 ноября 2026; спецификация ждёт проверки владельцем.

## Контекст

Последняя часть подпроекта 5 «как в 4K». После неё — отложенные мелочи 5а/5б одним заходом, затем новая версия и сборки.

Сейчас (`dev`):

- `Scheduler` (`application/scheduler.py`) ведёт ровно одно активное задание: `_active: tuple[job_id, attempt_id] | None` и флаги попытки `_launched`, `_discovered`, `_stopping`. `_pump` запускает следующее задание, только когда `_active is None` и `executor.is_idle`.
- `ThreadExecutor` (`infrastructure/executor.py`) уже хранит загрузки в словаре `_workers`, но `start` отказывает, если исполнитель не свободен; `available` излучается, только когда стал свободен. Проверка качества (`request_probe`) идёт только при свободном исполнителе, и пока она идёт, загрузки не стартуют.
- «Ограничение скорости» из 5а — `ratelimit` yt-dlp (своё у каждой загрузки, фиксируется при старте; при лимите фрагменты качаются по одному). Фото Instagram качаются своим циклом (`MediaPipeline`, чтение по 64 КБ) без лимита.
- Интерфейс проверяет `executor.is_idle` перед «Удалить файлы», «Очистить список», для запрета сна и уведомления «загрузки завершены».

## Цель

Ролики YouTube качаются по несколько сразу (до N, N выбирается в настройках от 1 до 4), рядом с ними — по одной загрузке Instagram и GetCourse; лимит скорости — общий на всё.

## Решения владельца

- Instagram и GetCourse идут рядом с YouTube, каждая площадка — по одной загрузке («Рядом, по одной»).
- «Ограничение скорости» — на все загрузки вместе.

## Поведение

### Настройка

1. В разделе «Соединение» под «Скоростью» — строка **«Одновременные загрузки YouTube»** с ползунком 1–4 (шаг 1, деления) и подписью текущего значения справа: 1 — «Безопасно», 2 — «Обычно», 3 — «Быстро», 4 — «Рискованно». Пояснение под строкой: «Сколько роликов YouTube качать сразу». При 3 и 4 ниже появляется предупреждение (цвет предупреждения темы): «YouTube может временно заблокировать загрузки с вашего IP».
2. По умолчанию 1 — программа ведёт себя как сейчас. Значение хранится в `settings-v2.json` (`youtube_parallel`); отсутствующее поле — 1, значение вне 1–4 или не целое — настройки по умолчанию, как для остальных полей.
3. Изменение действует сразу: увеличение — очередь тут же добирает загрузки; уменьшение — идущие загрузки не прерываются, новые ждут, пока активных YouTube станет меньше N.
4. Английские тексты: «Simultaneous YouTube downloads», «How many YouTube videos to download at once», «Safe / Normal / Fast / Risky», «YouTube may temporarily block downloads from your IP».

### Очередь

5. У каждого задания своя полоса по площадке ссылки: YouTube (мест N), Instagram (1), GetCourse (1). Разбор плейлиста YouTube занимает место YouTube, как и ролик.
6. Очередь просматривается по порядку; запускается каждое ожидающее задание, в полосе которого есть место. Задание, полоса которого занята, ждёт, но не задерживает задания других полос позади себя. Порядок внутри полосы сохраняется. «Запустить» у конкретного задания ставит его первым в своей полосе.
7. Пауза, отмена, «Остановить всё», «Повторить», ожидание лимита Instagram и выбор материалов урока работают с каждой активной загрузкой отдельно; место освобождается, только когда исполнитель подтвердил окончание (как сейчас для одной).
8. Закрытие программы ставит на паузу (`shutdown`) все активные и ждёт их подтверждения; при следующем запуске они продолжаются как сейчас.
9. Проверка качества по ссылке (выбор качества в карточке) — как сейчас: идёт, только когда загрузок нет; пока она идёт, новые загрузки не стартуют.

### Общий лимит скорости

10. При выбранном лимите сумма скоростей всех идущих загрузок (ролики, плейлисты, фото и видео Instagram, GetCourse) не превышает его в среднем за секунду. Когда загрузка заканчивается, остальные сами получают её долю. Смена лимита действует с ближайшей секунды, в том числе для идущих загрузок.
11. Ожидание лимита прерывается отменой и паузой не дольше чем за 0,2 с.
12. `ratelimit` yt-dlp больше не передаётся; фрагменты при лимите по-прежнему качаются по одному.

### Не меняется

13. «Удалить файлы», «Очистить список» и закрытие ждут, пока не останется ни одной загрузки; запрет сна держится, пока идёт хоть одна; уведомление «загрузки завершены» — когда очередь закончилась целиком.

## Устройство

- **`AppSettings.youtube_parallel: int = 1`** (`infrastructure/settings.py`): проверка в `_check_options`, ключ в `_EXTRAS`.
- **`Scheduler`**:
  - `_active: dict[str, _Attempt]` — по `job_id` попытка (`attempt_id`, `launched`, `discovered`, `stopping`); все места, где было `self._active`, работают с записью своего задания.
  - `limits: dict[Service, int]` (по умолчанию YouTube 1, Instagram 1, GetCourse 1) и `set_youtube_parallel(n: int)` (1–4, затем `_pump`).
  - `_pump`: пока есть место, выбирает первое ожидающее задание, чья полоса не заполнена (с учётом `_preferred_job`), и запускает его; цикл заканчивается, когда подходящих нет или исполнитель занят проверкой качества (`executor.probing`).
  - `handle` принимает события любого активного задания по паре `(job_id, attempt_id)`; события чужих попыток отбрасываются как сейчас.
- **`ThreadExecutor`**:
  - `start` отказывает только при закрытии; `is_idle` — по-прежнему «нет ни загрузок, ни проверки».
  - Новое свойство `probing` (идёт или ждёт проверка качества).
  - `available` излучается после окончания любой загрузки, если исполнитель не закрывается.
  - Один общий `RateLimiter` на исполнитель передаётся каждой загрузке через `ExecutionContext.limiter`; лимит в нём меняется, когда presenter меняет `preferences`.
- **`RateLimiter`** (`infrastructure/rate_limiter.py`, потокобезопасный, часы и сон внедряются для тестов): `set_rate(bytes_per_second: int | None)`, `consume(count: int, cancel: CancellationToken)` — ведро токенов ёмкостью в одну секунду лимита; при нехватке поток спит кусками по 0,1 с, проверяя `cancel`. Без лимита `consume` ничего не делает.
- **`ExecutionContext.limiter`** (`providers/base.py`) — протокол с `consume`; по умолчанию — ничего не делающий. `MediaPipeline._telemetry` передаёт ему прирост `downloaded_bytes`; тот же крючок уже вызывается в цикле фото, так что фото тоже ограничиваются.
- **Настройки**: `SettingsPage` — ползунок `parallel_slider` (`QSlider`, 1–4), подпись `parallel_label`, предупреждение `parallel_warning`; presenter передаёт значение в `scheduler.set_youtube_parallel` в `_apply_runtime_settings`.

## Проверки

- Планировщик (поддельный исполнитель): при N=3 из очереди «YT, YT, IG, YT, YT, GC, IG» стартуют три YT, один IG и один GC; окончание YT запускает следующий YT; второй IG ждёт первый; уменьшение N до 1 не останавливает идущие и не запускает новые, пока активных YT ≥ 1; пауза/отмена/«Остановить всё»/закрытие при трёх активных — каждая останавливается, места свободны только после подтверждений; события старой попытки отбрасываются; проверка качества не даёт стартовать новым.
- Исполнитель: две загрузки сразу; `available` после окончания одной из двух.
- `RateLimiter` (поддельные часы): сумма потребления двух потоков за 5 с ≈ лимит; смена лимита на ходу; без лимита не спит; отмена прерывает ожидание.
- `MediaPipeline`: `ratelimit` не передаётся; крючок вызывает `consume` с приростом байтов.
- Настройки: сохранение и чтение `youtube_parallel`; неверное значение — по умолчанию; ползунок меняет подпись, предупреждение видно на 3–4; изменение доходит до планировщика.
- Живой прогон на Mac: N=3, плейлист YouTube из 4 роликов и ссылка Instagram — идут сразу три ролика и пост; лимит 2 МБ/с — общая скорость в строках ≈ 2 МБ/с.

## Не входит

Одновременные загрузки внутри Instagram и GetCourse; отдельные лимиты скорости на площадку; одновременность для проверки качества и фоновых названий; «Скорость» в строке-итоге всего списка.
